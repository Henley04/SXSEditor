Plugin Backends 插件后端

SXSEditor's plugin system lets a third-party singing backend replace the built-in SoulX-Singer pipeline — including classical concatenation approaches that use no neural model at all. A plugin declares its own track kinds, receives every parameter the built-in model would have received, and returns audio through a validated channel. This document specifies contract version 1 and is the normative reference for plugin authors.

SXSEditor 插件系统允许第三方歌声后端替换内置的 SoulX-Singer 管线——包括完全不使用神经网络的传统拼接方案。插件声明自己的轨道种类，收下内置模型本会收到的全部参数，并通过受校验的通道返回音频。本文档规定契约版本 1，是插件作者规范性参考。

ℹ️

Source files: src/shared/pluginContract.js (the single source of truth for validation), src/main/pluginHost.js (host kernel), src/main/pluginWorker.js (worker runtime and cross-thread codec), src/main/pluginIpc.js (IPC surface), and plugins/example-concat/ (a runnable template plugin).

相关源文件：src/shared/pluginContract.js（校验唯一真源）、src/main/pluginHost.js（宿主内核）、src/main/pluginWorker.js（worker 运行时与跨线程编解码）、src/main/pluginIpc.js（IPC 接口），以及 plugins/example-concat/（可直接运行的模板插件）。

Execution Model 执行模型

Plugins run in a worker_threads worker by default. This is a correctness requirement rather than a preference. Consider a plugin that busy-waits synchronously:

插件默认运行在 worker_threads worker 中。这是正确性要求而非偏好。设想一个同步忙等的插件：

const t = Date.now();
while (Date.now() - t < 2000) { /* ordinary plugin code */ }

Loaded in the main process, this code monopolises the event loop: the host's setTimeout cannot fire, so the timeout arm of Promise.race([call, timeout]) never runs — a 2-second busy-wait survives a 300ms timeout. No mechanism inside a single thread can preempt synchronous code. The only reliable interruption is terminating the thread from outside.

若载入主进程，这段代码会独占事件循环：宿主的 setTimeout 无法到点执行，Promise.race([call, timeout]) 的超时分支永远不会跑——实测 2秒忙等在 300ms 超时下照样返回。单线程内部没有任何手段能抢占同步代码，唯一可靠的打断方式是从外部终止该线程。

Boundary of inprocess. This mode uses Promise.race plus a timer, which only intercepts awaiting a promise that never settles. A synchronous busy-wait or infinite loop keeps the main thread frozen until the plugin returns on its own; no timeout can help. Selecting this mode means accepting that constraint and guaranteeing yourself that no unbounded synchronous work runs on the main thread. The host logs a warning at load time so this boundary appears in the runtime record rather than only in documentation.

inprocess 模式的边界。该模式用 Promise.race + 定时器，只能拦住「await 一个永不settle 的 Promise」。同步忙等或死循环会让主线程一直冻结到插件自己返回，任何超时都不起作用。选择该模式即等于接受这一约束，并由你自行保证不在主线程上运行不可控长度的同步代码。宿主在加载时会打一条 warn，使这条边界出现在运行现场，而不只是文档里。

Measured cost of worker mode worker 模式的实测代价

  • Large arrays are zero-copy. Float32Arrays in the request and the returned pcm travel via the postMessage transfer list, so ownership moves instead of the bytes being copied. A transferred request array becomes detached (byteLength === 0) — that is the evidence no copy occurred. A 4MB buffer measures in the low milliseconds. 大数组零拷贝。请求中的 Float32Array 与返回的 pcm 走 postMessage 的 transfer list，所有权转移而非复制。转移后请求侧数组变为 detached（byteLength === 0）—— 这正是「没有发生复制」的判据。4MB 实测在毫秒级。
  • Functions cannot cross threads. Functions in options (onProgress, refF0Extractor, …) stay in the main process; the plugin receives a proxy of the same name. Calling host.emitProgress(50) posts a message that the main process forwards to the real function. The call signature the plugin sees is identical in both modes, so a plugin must not branch on its execution mode. 函数不能跨线程。options 中的函数（onProgress、refF0Extractor 等）留在主进程，插件侧拿到同名代理。调用 host.emitProgress(50) 会 postMessage 到主进程再调用真函数。两种模式下插件看到的签名完全一致，因此插件不应按执行模式写分支。
  • Non-cloneable values (symbols, exotic host objects) are replaced with a skip marker and logged, rather than failing the whole call. 不可克隆的值（Symbol、特殊宿主对象）会被换成 skip 标记并记录日志，而不是让整次调用抛错。

Installation Layout 安装目录结构 

<userData>/plugins/          # plugin root; authorized before loading
└── <pluginId>/              # directory name must equal manifest.id
    ├── manifest.json        # required
    └── index.js             # entry named by manifest.main (CommonJS)

On Windows <userData> is %APPDATA%\SXSEditor. The host scans only this directory: the repository's plugins/example-concat/ is a template and is never loaded automatically — copy the directory into <userData>/plugins/ to install it, or place it there from the in-app Open Plugins Folder button and then reload. In the app, the plugin section lives in the Add Singer dialog (#btn-add-singer in the main window); the Reload button there re-scans without restarting.

Windows 下 <userData> 为 %APPDATA%\SXSEditor。宿主只扫描该目录：仓库内的 plugins/example-concat/ 是模板，永远不会被自动加载——把整个目录复制到 <userData>/plugins/ 即完成安装，或在应用内点「打开插件目录」放入后再重载。应用中的插件分区位于「添加歌手」对话框（主窗口的 #btn-add-singer），其中的「重新加载」按钮可在不重启的前提下重新扫描。

Entry Module 入口模块导出 

module.exports = {
  id, name, version, apiVersion: 1,
  capabilities: { synthesize, blockPlayback, streaming, voices },
  trackKinds: [ /* validated declarations */ ],
  async initialize(ctx),// optional; failure sets state='failed'
  async getVoices(kindId),   // required when capabilities.voices=true
  async synthesize(request, host) -> SynthResult,
  async dispose(),            // optional; hot reload and shutdown
};

The host is lenient where it can be and strict where it must be: declaring capabilities.synthesize without a synthesize() function rejects the plugin; declaring voices without getVoices() only downgrades the capability and warns. Track kinds exported from the module take precedence over the manifest, because the module is the runtime truth. A missing initialize counts as success, a missing dispose as a no-op.

宿主在可以宽松处宽松、在必须严格处严格：声明 capabilities.synthesize 却没有 synthesize() 会拒绝加载；声明 voices 却没有 getVoices() 只降级能力并告警。模块导出的 trackKinds 优先于 manifest，因为模块是运行时真源。缺省 initialize 视为成功，缺省 dispose 视为空操作。

Under worker mode these are proxies: the arguments are posted to the main process, which performs the real call. A ticket's id is pre-allocated before the call, so it is available synchronously in the plugin; update() and end() are likewise messages. isCancelled() is an asynchronous query, so refresh it at await points. Plugins must not depend on return values from host.*, and must not branch on execution mode.

worker 模式下这些是代理：参数 postMessage 回主进程，由主进程执行真调用。ticket 的 id 在调用前预分配，因此插件侧是同步拿到的；update() / end() 同样是消息。isCancelled() 是异步查询，请在 await 点刷新。插件不依赖 host.* 的返回值，也不应按执行模式写分支。

Result and validation 返回值与校验 

{
  pcm: Float32Array | Float32Array[] | null,  // null only for streaming plugins
  channels: number,       // >1 means interleaved (array form = per channel)
  sampleRate: number,     // finite integer within 8000..768000
  leadingSamples: number, // leading zeros needed before pcm[0]
  diagnostics: object,
}

An invalid result is rejected outright and never reaches the mixing chain. sampleRate and leadingSamples are checked before pcm, because the duration limit needs sampleRate to convert sample count to seconds.

不合法的结果会被直接拒绝，绝不会进入混音链路。sampleRate 与 leadingSamples 先于 pcm 校验，因为时长上限需要用 sampleRate 把样本数换算成秒。

Check校验项 Rule规则 Rationale原因
Type类型 Float32Array or a per-channel array of them必须是 Float32Array（或逐声道的 Float32Array[]） The built-in chain only consumes Float32内置链路只吃 Float32
Finite values有限值 Every sample scanned for NaN and ±Infinity逐个样本扫 NaN / ±Infinity One NaN turns an export into crackling or a silent block, and NaN leaks out of divisions readily一个 NaN 就会让整段导出变成爆音或静音块，而 NaN 很容易从除零里滑出来
Length长度 Mono ≤ sampleRate × 3600 (1 hour) and ≤ 256MiB total单声道 ≤ sampleRate × 3600（1 小时），总字节 ≤ 256MiB Earlier builds accepted multi-hundred-megabyte returns; real singing segments are far smaller旧实现连数百MB的返回值也照收；正常歌声片段远达不到这个量
Sample rate采样率 Finite integer within 8000–768000必须是 8000–768000 的有限整数 NaN is rejected rather than silently falling back to a defaultNaN 不再静默回落成缺省值，而是直接拒绝
✅

Why the scan is exhaustive. Sampling would be N times cheaper but can miss an isolated NaN from a division by zero or log(0), which still corrupts the export. The measured cost of the full scan is 0.59ms per 1.0MiB, 3.15ms per 4.0MiB, and 12.57ms per 16.0MiB — roughly 3ms per million samples. Synthesizing 16MiB (about three minutes) takes seconds, so a linear pass is negligible. The hot loop makes no function calls (v !== v for NaN, direct comparison against ±Infinity) and allocates nothing.

为何全量扫描。抽样成本约为 1/N，但会漏掉除零或 log(0) 产生的孤立 NaN，一旦漏掉照样导出损坏音频。全量扫描实测 1.0MiB≈0.59ms、4.0MiB≈3.15ms、16.0MiB≈12.57ms（约每百万样本 3ms）。合成 16MiB（约三分钟）音频本身耗时以秒计，线性扫描可忽略。热循环里不做函数调用（v !== v 判 NaN、直接与 ±Infinity 比较），也不额外分配内存。

Host Guardrails 宿主护栏

  1. Lifecycle. Calls are rejected unless the plugin state is ready.生命周期。状态非 ready（未 initialize / initialize 失败 / 已 dispose）一律拒绝调用。
  2. Timeout. In worker mode the deadline calls worker.terminate() — a genuine preemption; a busy-looping plugin dies immediately. The host then rebuilds the worker and re-runs initialize, because one timeout may simply mean the limit was too low; only consecutive timeouts (3) mark the plugin failed. 超时。worker 模式下到点直接 worker.terminate()——这是唯一的真抢占，忙循环的插件会被即时掐断。之后宿主重建 worker 并重跑 initialize（单次超时可能只是超时值给小了，不该一棍子打死）；连续超时达到 3 次才把插件标成 failed。
  3. Exception isolation. A throwing plugin is logged and returns {success:false, error}; messages crossing IPC are sanitized and never carry the plugin's internal stack.异常隔离。插件抛错只记日志并返回 {success:false, error}；过 IPC 的错误经脱敏，不会带出插件内部堆栈。
  4. Result validation. See above.结果校验。见上节。
  5. Capability checks. Without capabilities.synthesize a plugin cannot synthesize; without blockPlayback it cannot create tickets.能力校验。未声明 capabilities.synthesize 不能合成，未声明 blockPlayback 不能创建 ticket。
  6. Path guard. The entry file must resolve inside the plugin directory after realpath, which blocks .., absolute paths, and symlink escapes. Both the plugin root and the entry file are authorized before loading. A plugin that reads models or assets must go through the host's path check; failing it is an error, and the existing allowlist cannot be widened.路径护栏。入口 main 在 realpath 后必须落在插件目录内，挡掉 ..、绝对路径与符号链接逃逸；插件根目录与入口文件加载前都会授权。插件读取模型或素材须走宿主路径校验，不通过即报错，且不允许放宽现有白名单。
  7. Fault isolation. One plugin failing to load, initialize, or synthesize marks only itself failed; the others keep working.故障域隔离。单个插件加载 / initialize / 合成失败，只把它自己标成 failed，其它插件照常可用。
  8. Hot reload. A reload disposes everything and rescans. Old plugin code disappears with terminate() in worker mode; inprocess additionally clears require.cache. Both modes reap leftover tickets.热重载。重载即 dispose 全部后重新扫描加载。worker 模式下旧代码随 terminate() 一起消失，in-process 模式则靠清 require.cache；两模式都会收掉所有残留 ticket。
  9. Update throttling. Ticket updates are pushed at most every 100ms and only when progress moves by at least 2%; the terminal states are always sent. Measured: 400 updates become 51 pushes.ticket 推送节流。一次 update() 以前是一条 IPC，现按最小间隔 100ms 且进度变化 ≥ 2% 节流，进度到 100 / 取消 / 结束必发。实测 400 次 update() → 推送 51 次。

Blocking Playback 阻滞播放

For preparation that must finish before audio starts, a ticket lets the UI show why it is waiting and for how long:

对于必须在播放前完成的耗时准备步骤，ticket 让界面显示等待原因与进度：

const ticket = host.blockPlayback({ title: 'Preparing source', message: 'Loading…', cancellable: true });
ticket.update({ message: 'Concatenating…', progress: 40 });
ticket.end();  // required
  • A null return means the plugin did not declare capabilities.blockPlayback; the call is refused and logged.返回 null 表示插件未声明 capabilities.blockPlayback，调用被拒绝并记日志。
  • Events plugin:blocking-start / -update / -end carry {ticketId, pluginId, title, message, progress, cancellable, reason, cancelled}.主进程事件 plugin:blocking-start / -update / -end，载荷 {ticketId, pluginId, title, message, progress, cancellable, reason, cancelled}。
  • When cancellable is set, the UI may cancel; the plugin observes this through host.isCancelled() or request.abortSignal.cancellable 为 true 时界面可取消，插件通过 host.isCancelled() / request.abortSignal 感知。
  • Fail-safe. When a synthesize call returns — success, failure, or timeout — the host ends every ticket that call created, so a forgotten end() cannot wedge the UI. A ten-minute watchdog and reload/dispose cover tickets created by background tasks. At most 8 tickets per call.兜底。一次 synthesize 调用返回（成功 / 失败 / 超时）后，宿主自动 end() 本次创建的所有 ticket，插件忘记 end() 也不会把界面永久卡死；另有 10 分钟 watchdog 与 reload/dispose 兜住后台另起的 ticket。单次调用最多 8 个。

Integration with the Built-in Pipeline 与内置管线的接线

All three synthesis handlers accept a plugin backend declared in options:

三个合成 handler 都支持在 options 里声明插件后端：

options.backend = { type: 'plugin', pluginId: 'example-concat', kindId: 'concat-basic', params: { waveform: 'pulse' } };
Handlerhandler Plugin branch插件分支行为
svs:synthesize After opts is fully assembled — including injected language, onProgress, refF0Extractor — the same object is handed to the plugin and the handler returns without invoking the built-in pipeline构造完 opts 后把同一个对象交给插件并直接 return，不调用内置 pipeline
fragment-svs:synthesize As above同上
svs:synthesizeMultiStreaming Fragments are grouped per declared backend: plugin fragments go to their plugin, built-in fragments to the built-in pipeline, and every group is summed on one timeline starting at beat 0. Mixing several backends in one project is therefore supported rather than an error逐分片按各自声明的后端分组：插件分片交给对应插件、内置分片交给内置管线，各组结果在 beat 0 起的同一条时间轴上叠加，多后端混排不再报错

The plugin's {pcm, channels, sampleRate, leadingSamples} is reduced to the same mono Float32Array the built-in chain uses (leading zeros applied by the host, first channel taken for multichannel), so the renderer never distinguishes backends. 插件返回的 {pcm, channels, sampleRate, leadingSamples} 由宿主压成内置链路的同款单声道 Float32Array（leadingSamples 由宿主补零，多声道取第一声道），因此渲染层无需区分后端。渲染层也可绕过 SVS 通道直接调用 pluginAPI.synthesize()（用于预览或面板自测）。

全部 handler 用 safeHandle 注册，与仓库其它 IPC 一致：主进程记全量错误，过 IPC 的只有脱敏后的 message。渲染层入口是 window.electronAPI.pluginAPI。

Writing a Plugin 开发自己的插件

  1. Copy the template: cp -r plugins/example-concat <userData>/plugins/my-backend, then change both the directory name and manifest.id to my-backend.复制模板：cp -r plugins/example-concat <userData>/plugins/my-backend，把目录名与 manifest.id 一起改成 my-backend。
  2. Replace the body of synthesize() with your own inference or concatenation logic. A plugin may require its own dependencies; everything inside the plugin directory is the plugin's own responsibility.把 synthesize() 换成你自己的推理或拼接逻辑。插件可以 require 自己的依赖，插件目录内的一切由插件自己负责。
  3. Expose user-adjustable parameters through trackKinds[].paramSchema; the host turns UI values into request.params and drops undeclared keys.要提供用户可调参数，就在 trackKinds[].paramSchema 里声明；宿主把界面取值算成 request.params，未声明的键会被丢弃。
  4. Use host.blockPlayback() for preparation that must complete before playback.需要在播放前完成的准备步骤，用 host.blockPlayback()。
  5. Reload from the plugin section in the Add Singer dialog — no application restart required.在「添加歌手」对话框的插件分区点「重新加载」即可生效，无需重启应用。
🚫

Practices to avoid. Do not mutate request.options and expect the built-in pipeline to consume it afterwards. Do not structuredClone or JSON.parse(JSON.stringify()) large objects on the hot path. Do not declare an apiVersion other than 1. Do not perform minute-long loading in initialize without telling the user through blockPlayback — the UI will appear frozen.

不要做的事。不要改写 request.options 后指望内置 pipeline 还能用它；不要在热路径上 structuredClone / JSON.parse(JSON.stringify()) 大对象；不要声明 apiVersion 以外的版本号（会被拒绝）；不要在 initialize 里做分钟级加载而不用 blockPlayback 告诉用户（界面会看起来像卡死）。

Regression smoke test 回归冒烟

After changing the host or the contract, run:

改动宿主或契约后跑一次：

node scripts/plugin-smoke.js     # no electron, no node_modules required

Twenty-six assertions cover discovery and loading, voices, same-reference options pass-through, blocking-ticket start/update/end balance, whether a synchronously busy-waiting plugin is genuinely preempted by the timeout (a plugin busy-waiting five seconds must die under a one-second limit), rejection of PCM containing NaN, and recognition and synthesis of a midi-partial track kind. The busy-wait case is the only assertion that can distinguish a real timeout from a Promise.race illusion; it turns red immediately if the default mode is ever changed back to inprocess.

26 项断言覆盖插件发现与加载、音色、options 同引用透传、阻滞 ticket 的 start/update/end 配平、同步忙等插件能否被超时真实抢占（构造一个忙等 5 秒的插件，在 1 秒超时下必须被杀）、含 NaN 的 PCM 必须被拒，以及 midi-partial 轨道种类的识别与合成。其中「忙等抢占」是唯一能区分真超时与 Promise.race 假超时的用例——若哪天有人把默认执行模式改回 inprocess，这条会立刻变红。
